## 文書の読み方と根拠

文書中の事実は、次のいずれかとして扱います。

| 表記 | 意味 | 更新時の扱い |
|---|---|---|
| コード確認済み | リポジトリ内の実装で確認できる現在の挙動 | 実装を変えたら同じ変更単位で更新 |
| 公式資料 | 外部サービスの公式資料に基づく上限や仕様 | URL と確認日を記載し、変更時に再確認 |
| ローカル実測 | 隔離したローカル環境で得た値 | 条件・日付・限界を併記し、本番値と混同しない |
| 未確認 | 本番設定、実機、実データなど、現時点で証拠がない事項 | 推測で補完せず、必要な検証を明記 |

設計意図と不変条件は docs の規範です。一方、実際の挙動の一次情報はコードと実行結果です。記述と実装が食い違うときは、まず実装と検証結果を確認し、意図を変えない範囲で docs を直してください。設計・要件そのものを変える必要があるときは、独断で決めずに確認を求めます。

## 公開文書としてのルール

- 実同期コード、秘密鍵、Push endpoint、ユーザーデータ、バックアップ、ログの生値を記載しない。
- サンプル値は `example.com`、`<placeholder>`、架空の同期コードだけを使う。
- 公開リポジトリに不要な攻撃再現手順・詳細な枯渇コスト・過去監査の生データは置かない。設計上必要な上限と防御だけを記載する。
- `wrangler.toml`、`.env`、`.dev.vars`、`backup-*.sql` は追跡しない。公開する設定例は秘密を含まないテンプレートに限る。

## 更新ルール

- 変更前に、影響表にある関連文書と不変条件を読む。
- 変更後に、仕様・実装・検証方法・既知の制約のうち影響する記述を更新する。
- 文書の追加・更新では、リンク、コマンド、見出しアンカー、数値の根拠を確認する。
- Git のステージング、コミット、push、デプロイは人間が行う。エージェントは変更内容と検証結果を報告する。

## 用語

| 用語 | 意味 |
|---|---|
| 同期コード | 12 文字のコード。ログインの代わりにデータの所属と API 利用可否に使う。実質的なアクセス情報として扱う。 |
| LWW | Last-Write-Wins。`updated_at` が新しい行を採用する競合解決。 |
| push カーソル | ローカル変更をサーバーへ送った位置を示す、クライアント時計の値。 |
| pull カーソル | サーバーから取得済みの位置を示す、`server_seq` の値。 |
| revive | 繰り返しタスクを次の周期で `completed` から `active` へ戻すクライアント処理。 |
| stale recovery | 過去に残った繰り返しリマインダーを将来の周期へ進める Cron 処理。 |
