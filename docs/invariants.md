# 設計上の不変条件と落とし穴

**このファイルは最優先で読んでください。** ここに書かれているものは、いずれも「一見すると改善に見えるが、
壊すと静かに不具合が出る」ものです。多くは実際に事故を起こしてから直したものです。

各項目は「何を守るか / なぜ / 破ったときに何が起きるか」で書いてあります。

---

## I-1. 繰り返しタスクの status 復活はクライアント専任

**守ること**: サーバー（Workers）は `tasks.status` を絶対に書き換えない。

**なぜ**: 同期は行単位の LWW（`updated_at` 比較）です。サーバーが `completed → active` を書くと、
そのためだけに `updated_at` を進める必要があり、進めるとクライアント側の未同期の編集を上書きして
取りこぼします。逆に `updated_at` を進めずに書くと、他端末が古い値で上書きし返して振動します。

**破ると**: 端末をまたいだ編集が黙って消える。再現が難しく、原因の特定はほぼ不可能。

**代わりにどうしているか**: サーバーは status を見るだけ（`completed` の繰り返しタスクにも「その周期より前に
完了しているなら」通知を送る）。実際の `completed → active` の書き換えはクライアントの `reviveRecurringTasks()`
が行います。詳細は [recurrence.md](./recurrence.md)。

**周期をまたぐときに戻す値も同じ扱い**: 定量タスクの `current_value` を 0 に戻す処理と、サブタスク
（`subtasks`）の `done` を全て `false` に戻す処理も、どちらも `reviveRecurringTasks()` の中だけで行います。
**サーバーにこれらを書かせない。** 理由は status とまったく同じで、書けば `updated_at` の扱いに関して
上と同じジレンマに陥ります。どちらも `completed → active` の分岐の中にあり、`active` のまま持ち越した
タスクには適用しません（途中まで進めた手順や現在値を、周期が変わっただけで消さない）。

## I-2. push カーソルと pull カーソルは別の時計

**守ること**: `lastPushedAt`（push カーソル）は**クライアント時計**、`lastSyncedAt`（pull カーソル）は
**サーバー採番の `server_seq`**。この 2 つを混ぜない。

**なぜ**:
- push は「ローカルの `updated_at` より新しいものを送る」ので、比較相手はローカル時計でなければならない。
- pull は「サーバーに届いた順」で取りこぼしを防ぐ必要がある。`updated_at`（クライアント時計）をカーソルに
  使うと、端末間の時計ズレや「編集してから push するまでの遅延」で、他端末が永久に受け取れない行ができる。

**破ると**: 特定の行だけが一部の端末に永久に届かなくなる。ユーザーからは「たまに同期されないタスクがある」
としか見えない。

**境界の扱い**（2026-08-13 に是正）:

- **push カーソルは「送った時刻 − 1ms」を保存する**（`sync.ts`）。スナップショット（`toArray`）を取った後、
  カーソルを保存するまでの間に `updated_at === pushNow` の編集が入ると、次回の抽出条件
  `updated_at > since` から漏れて二度と送られない。1ms 戻せば境界の行がもう一度送られるだけで、
  upsert は冪等なので害はない。端末の時計が巻き戻ったときにカーソルが先へ行き過ぎるのも同時に緩和される。
- **同値の `updated_at` はサーバーを勝ちにする**。サーバーの LWW は `>=` で同値を受理して上書きするので、
  クライアントの pull 取り込みも `local.updated_at > server.updated_at` のときだけ捨てる（`>=` ではない）。
  `>=` だと 2 端末が同じミリ秒に別の値を書いたとき互いに自分の値を持ち続け、以後そのタスクを誰かが
  編集するまで永久に収束しない（全量 pull でも直らない）。
- **pull カーソルには意味づけの版（`todo_cursor_schema`）を持たせる**。migration 0002 で pull カーソルは
  「サーバー時刻」から `server_seq` へ変わったが、端末が保存済みのカーソル値はリセットされなかった。
  版が古い端末では起動時に一度だけカーソルを 0 に戻す（`storage.ts` の `migrateCursorSchema`）。

## I-3. `server_seq` は INSERT 文の中で採番する

**守ること**: `server_seq` を「先に `SELECT MAX(...)` してから INSERT」で採番しない。
現在の実装は INSERT 文内のスカラサブクエリで採番している（`workers/lib/lww.ts`）。

```sql
MAX((SELECT COALESCE(MAX(server_seq), 0) + 1 FROM tasks WHERE sync_code = ?), ?)
```

**なぜ**: 事前に MAX を読むと、並行する 2 つの push が同じ MAX を読んで**同一の seq を採番**します。
その seq まで pull 済みの端末は、後から書かれた行を恒久的に取りこぼします。

**`Date.now()` を下限に敷いている理由**: クリーンアップで最大 seq を持つ行が消えても、既存端末が持つ
ms スケールのカーソルより必ず後ろへ並ぶようにするため。

**確認済み**: `EXPLAIN QUERY PLAN` で `SEARCH tasks USING COVERING INDEX idx_tasks_server_seq (sync_code=?)`
となり min/max 最適化が効くため、このサブクエリのコストは O(1) 相当です。

---

## I-3b. LWW の採否判定は書き込みと同じ 1 文の中で行う

**守ること**: 「事前に `SELECT` して JS で採否を決め、無条件に書き込む」形にしない。現在の実装は
`ON CONFLICT(id) DO UPDATE ... WHERE` で、`updated_at` の比較とテナント分離（I-15）を書き込みと同じ文の
中で評価する（`workers/lib/lww.ts`）。応答の `accepted` も、`db.batch()` の各文が返す `meta.changes` を
数えた**実際に書けた件数**にする。

**なぜ**: 事前 `SELECT` は `batch` の外にあるため、判定と書き込みの間に別リクエストの `batch` が割り込めます。
両方が同じ古いスナップショットに合格すると、**後着の古い値が新しい値を上書き**します。`server_seq` は
上書きのたびに前進するので、その古い値が「最新のサーバー行」として全端末へ配られ、次に誰かがその
タスクを編集するまで直りません。並行リクエストを仮定しなくても、**同一リクエストに同じ id を
`updated_at` 200 → 100 の順で 2 件入れるだけ**で再現します（そのため JS 側でも id の重複を最新 1 件へ畳む）。

**`accepted` を実測にする理由**: I-14 の同期コード切替は「全件がサーバーへ移った」ことを確認してから
ローカルを消します。`accepted` が「送った件数」を返す楽観値のままだと、その保全判定が成立しません。

**検証**: `migrations/0001–0005` を適用した実 SQLite に対し、上記の逆転反例・同値受理・テナント分離・
`server_seq` 単調性を確認済み（2026-08-13）。

## I-4. `reminder_time` は `Date.toISOString()` の出力そのもの

**守ること**: `reminder_time` に入る文字列は `YYYY-MM-DDTHH:mm:ss.sssZ`（24 文字）で、かつ
**暦として実在する時刻**だけ。サーバー側の `isValidPayload` が `isCanonicalIsoInstant()`
（`workers/lib/constants.ts`）で強制しています。

**なぜ**: Cron の候補クエリは `t.reminder_time > ? AND t.reminder_time <= ?` という**文字列の範囲比較**で
インデックスを使います（`datetime()` で包むとインデックスが効かず毎分フルスキャンになる）。この比較が
「辞書順 = 時刻順」として成立するのは、全書き込み元が固定長・固定書式の UTC ISO を書いているからです。

**書式だけでは足りない**（2026-08-13 に是正）。正規表現は桁の形しか見ないため、次が素通りしていました。

| 値 | 正規表現 | `Date.parse` | 結果 |
|---|---|---|---|
| `2026-00-01T00:00:00.000Z` | 通る | `NaN` | 前進計算が不能 |
| `2026-13-01T…` / `2026-01-32T…` | 通る | `NaN` | 同上 |
| `2026-02-31T00:00:00.000Z` | 通る | 有効 | `2026-03-03` へ**正規化**され、保存時刻と発火時刻がずれる |
| `2026-01-01T24:00:00.000Z` | 通る | 有効 | 翌日 0:00 へ繰り上がる |

そこで `Date.parse` → `new Date(ms).toISOString()` の往復が入力と一致することまで要求します。

**破ると**: その行はインデックス上の順序が壊れて通知が飛ばなくなるだけでなく、`nextReminderAfter()` が
入力をそのまま返すため**取りこぼし回収から永久に抜けなくなります**。回収クエリは
`ORDER BY reminder_time LIMIT n` なので、辞書順で早い位置に前進不能な行が n 件あるだけで
**それ以降の正常な行が一切回収されなくなります**（`2026-00-…` は `2026-01-…` より前に並ぶ）。

**既存行の始末**: 入力検証は新規の混入しか防げないため、cron 側でも前進不能と分かった行
（種別を解釈できない・`Date.parse` が NaN）の `reminder_time` を `NULL` にして集合から外します
（`workers/cron/notify.ts`）。クライアントが起動時に現周期を計算し直して push するので通知は復旧します。

## I-5. `sent_reminders` の claim は「送る前」に原子的に取る

**守ること**: `INSERT OR IGNORE INTO sent_reminders (task_id, reminder_time, ...)` を送信の**前**に発行し、
`meta.changes === 0` なら送信しない。この順序を入れ替えない。

**なぜ**: Cron の重複起動や窓の重なりが起きても二重に送らないための唯一のガードです。送信後に記録する
方式にすると、送信と記録の間で落ちたときに二重送信になります。

**現在の限界（既知）**: Push サービスが受理した**後**に接続が切れると `'failed'` になり claim が取り下げ
られるため、実際には二重通知が起こり得ます。厳密には at-most-once ではなく best-effort です。

**配信保証は best-effort（端末単位の再送はしない）**: claim は `(task_id, reminder_time)` の
**タスク単位**なので、同期コードに 2 台以上ぶら下がっていて 1 台にだけ届いた場合、届かなかった端末への
再送はありません（`okCount > 0` なら配信済みとして扱う）。claim 取得後に Worker が中断した場合も同様です。
重複より欠落を選ぶ設計であり、厳密な配信保証が必要になったら claim を endpoint 単位へ作り替える必要が
あります（schema と Cron の複雑性、D1 文数が増えます）。失敗そのものは
`Promise.allSettled` の理由を `console.error` に出しているので `wrangler tail` で追えます。

## I-6. サーバーは `color` と `project_name` を解釈しない

**守ること**: これらは素通しで保存・返却するだけ。CHECK 制約も付けない。

**なぜ**: 「プロジェクト」は独立したエンティティではなく `project_name` の文字列一致による派生表示です。
色も将来パレットが増えます。サーバー側に制約を持たせると、クライアントを更新した瞬間に同期が
`CHECK constraint failed` で全滅します（`migrations/0005_add_color.sql` のコメント参照）。

**バリデーションとの兼ね合い**: `isValidPayload` は**長さと型だけ**を見ます。値の意味は見ません。
`recurrence_rule.type` だけは例外的に列挙を検証していますが、これは [I-4](#i-4-reminder_time-は-datetoisostring-の出力そのもの) と同じ理由
（サーバーの前進計算が解釈できない値は行を永久 stale にする）です。**新しい繰り返し種別を追加するときは
`workers/lib/constants.ts` の `RECURRENCE_TYPES` も同時に更新してください。**

## I-7. 入力検証は「拒否」ではなく「スキップ」

**守ること**: `isValidPayload` を通らない行は、リクエスト全体を 400 にせず、その行だけ保存せずに
`invalid` としてカウントする。

**なぜ**: クライアントは 40 件をまとめて送ります。1 件の壊れた値でリクエスト全体を落とすと、同送した
正常な 39 件も保存されません。

**ただし**: `tasks` 配列の**件数**超過だけは 400 で拒否します（D1 のクエリ数上限に直結するため）。

## I-8. チャンクサイズと受付上限は 3 箇所で同値に保つ

**守ること**: `src/lib/sync.ts` の `PUSH_CHUNK_SIZE`、`workers/lib/chunk.ts` の `CHUNK_SIZE`、
`workers/lib/constants.ts` の `LIMITS.MAX_TASKS_PER_PUSH` はどれも **40**。片方だけ変えない。

**なぜ 40 か**: D1 Free の上限は「**50 クエリ / Worker 呼び出し**」です。push 1 回が発行する D1 文数は
`1 (users upsert) + ceil(N/CHUNK) (既存行 SELECT) + N (batch 内の文)`。CHUNK=40 のもとでは:

| N | 発行文数 | 判定 |
|---|---|---|
| 1 | 1 + 1 + 1 = 3 | 受付範囲 |
| 40 | 1 + 1 + 40 = 42 | 受付範囲の上限 |

[Cloudflare D1 Limits](https://developers.cloudflare.com/d1/platform/limits/) は、batch 内の各 statement に
個別クエリの制限が適用されると説明しています（2026-08-13 確認）。上限を変える場合は、クライアント、
Worker 側の statement 数と現在の D1 制限を同時に見直し、40 件の契約を片側だけ変更しないでください。

## I-9. `workers/lib/constants.ts` と `src/lib/constants.ts` は二重管理

**守ること**: 上限値（`TITLE_MAX_LENGTH: 200` / `PROJECT_NAME_MAX_LENGTH: 30` など）を片方だけ変えない。

**なぜ二重管理なのか**: `workers/` からはパスエイリアス `@/` が使えず（`tsconfig.workers.json` に定義がない）、
`src/lib/constants.ts` を import できません。相対パスで跨ぐと 2 つの tsconfig の境界を破ることになるため、
意図的に別ファイルにしています。

**破ると**: クライアントで 200 文字まで入力できるのにサーバーが 100 で弾く、といった状態になり、
ユーザーからは「一部のタスクだけ同期されない」ように見えます（`invalid` のトーストは出ます）。

## I-10. Cron の候補クエリと stale クエリは条件を揃える

**守ること**: 「候補（送信対象）」と「取りこぼし回収（前進対象）」の下限時刻を同じ位置に置く
（どちらも `nowSec - 60 - RETRY_GRACE_SEC`）。

**なぜ**: 回収の下限を候補より新しい側に置くと、**再試行中のリマインダーを先回りして前進させてしまい**、
再試行が成立せずに通知が黙って消えます。

---

## I-10b. Cron の候補処理は D1・外部 fetch の予算で見送る

**守ること**: 候補を claim・送信・前進する部分では、`CRON_D1_BUDGET` / `CRON_FETCH_BUDGET`（現実装では各 45）を
一つのカウンタで予約し、予算に入らない候補は claim せずに見送る。個別の上限
（`STALE_ADVANCE_LIMIT` = 20、`MAX_SUBSCRIPTIONS_PER_CODE` = 20）だけに頼らない。

**なぜ**: 個別の上限は互いに独立なので、**すべて守ったまま**合計が Free の上限
（50 D1 クエリ / 呼び出し、50 subrequests / 呼び出し）を超えられます。

繰り返し候補、stale 回収、購読先への fan-out は同じ実行で重なります。個別の上限だけでは、
その合計が D1 または外部 fetch の上限に達し得ます。変更時は候補数と購読数を含むシナリオで、
実装上の予約数を確認します。

**予算の使い方**: 予約は各候補の**最初の `await` より前**（同期部分）で行う。`candidates.map()` は各
コールバックを最初の `await` まで同期的に実行するため、予約順が候補の並び順で決定的になり、
並行実行でも取り合いになりません。予算に入らなかった候補は **claim せずに見送る**（claim してしまうと
「送っていないのに送信済み」になる）。候補クエリの窓は繰り返しで 660 秒、単発で 24 時間あるので、
次の分以降の実行で拾われます。stale の `LIMIT` も固定値ではなく残予算から決めます。

**既知の境界**: 候補の同期コード一覧を作るための購読 SELECT は予約前に実行されます。同期コード数が非常に多い場合、
この取得部分まで含めて 45 文以内であることは現行実装では保証していません。全実行の D1 上限を厳密に保証するには、
購読 SELECT のチャンク数も残予算に収める実装修正が必要です。

**破ると**: 上限に達した時点で同じ cron 内の一部の D1 文や fetch が失敗し、claim だけ残って通知が
欠ける（= リマインダーが黙って消える）状態に連鎖します。

## I-11. Cron の窓は `scheduledTime` を分に丸めて作る

**守ること**: `Math.round(controller.scheduledTime / 60000) * 60` で分境界へ丸める。`Date.now()` は使わない。
`floor` でもいけない。

**なぜ**:
- `Date.now()` を使うと実行時刻のゆらぎで隣り合う 60 秒窓が重なり、同じリマインダーを二度拾います。
- Cloudflare の Cron の実行時刻にはゆらぎがあります。秒へ `floor` すると窓の終端が分境界から外れ、
  分ちょうどのリマインダーが次の実行にこぼれて遅れる可能性があります。

窓は `(T-60, T]`（開始は排他・終了は包含）でタイル状に並び、各リマインダーはちょうど 1 窓に入ります。

## I-12. `cleanup` は繰り返しタスクの `completed` を消さない

**守ること**: 日次クリーンアップの削除条件は `status='deleted'` または
`status='completed' AND recurrence_rule IS NULL`。繰り返しの `completed` は残す。

**なぜ**: 繰り返しタスクの `completed` は「その周期だけ完了」の意味です（[I-1](#i-1-繰り返しタスクの-status-復活はクライアント専任) のとおり復活は
クライアント専任なので、アプリを開かない端末のサーバー行は `completed` のまま残ります）。消すと以後の
周期のリマインダーが止まります。

---

## I-13. Push 通知とローカル通知は排他

**守ること**: `pushManager.getSubscription()` があるときは `fireDueLocalNotifications()` を実行しない。

**なぜ**: サーバー Push の冪等ガードは D1 の `sent_reminders`、ローカル通知の冪等ガードは
localStorage の `todo_notified_reminders` で、**重複排除ストアが別系統**です。両方走ると、アプリを
開いている間だけ同じリマインダーが二重に届きます。

---

## I-14. `switchSyncCode` は「**全件がサーバーに書けた**ことを確認してから clear」

**守ること**: ローカルタスクを新コード宛に push し、**サーバーが実際に書き込んだ件数（`accepted`）が
送信件数と一致し、`conflicts` / `skipped` / `invalid` がすべて 0 のときだけ** `db.tasks.clear()` へ進む。
一致しなければ、ローカルには一切手を付けずに中止して理由を返す。

**なぜ**: 先に clear するとネットワーク断でローカルのタスクが消えたまま復旧できません。加えて、
**HTTP 200 は「サーバーが保存した」ことを意味しません**。次の 3 つはいずれも 200 で返る論理的な拒否です。

| 応答項目 | 意味 | 従来の挙動 |
|---|---|---|
| `conflicts` | サーバー側の行のほうが新しく上書きしなかった | 無視して clear → 画面から消える |
| `skipped` | 別の同期コードが所有していて書けなかった | トーストだけ出して clear |
| `invalid` | サーバーのバリデーションで落ちた | トーストだけ出して clear |

**2026-08-13 に是正**。とくに `conflicts` は「他端末が先に編集し、この端末がまだ pull していない」という
ありふれた状態で起き、そのタスクは新コードへ移らないままローカルからも消えていました。旧コードを
覚えていれば取り戻せますが、**サーバーに存在しないローカル専用の行は永久に失われます**。
中止時は「通常の同期が終わってからやり直す」よう案内します。

**既知の弱点**: `clear()` と full pull の間で失敗すると一時的に 0 件に見えます。ただし
`setLastSyncedAt(0)` 済みなので次回 `runSync` の pull で全件復旧し、サーバー側データは無傷です。

**関連**: 同期コードの保存（`storage.setSyncCode`）が失敗した場合も clear へ進みません。localStorage は
容量超過だけでなくブラウザ設定やプライバシーモードでも `SecurityError` で失敗し、そのまま進むと
「永続値は旧コード、ローカルは新コードの内容」という食い違いが残ります。

---

## I-15. `previous_sync_code` の申告がなければ行は移動しない

**守ること**: 既存行の所有コードが要求元と違う場合、`previous_sync_code` の申告が一致するときだけ
書き込みを許す（`workers/lib/lww.ts` のテナント分離）。

**なぜ**: タスク ID（UUID v4）を知っているだけの第三者が他人の行を乗っ取れないようにするため。
同期コード切替時の「タスク消失防止」と両立させる唯一の妥協点です。

**既知の弱点**: `previous_sync_code` は自己申告なので、**被害者のコードを知っている相手は行を自分側へ
移動できます**（被害者側からは消える）。ただしコードを知っている時点で pull で全読み・
`status='deleted'` 上書きも可能なので、追加の権限にはなっていません。allowlist は API 操作を
制限しますが、Worker への到達自体を防ぐものではありません。

---

## I-16. `ALLOWED_SYNC_CODES` が未設定なら全許可（意図的）

**守ること**: この後方互換をうっかり「未設定なら全拒否」に変えない。

**なぜ**: 設定漏れでサービス全停止（＝自分自身を締め出す）を避けるためです。ただし**設定しなければ
防御はゼロ**なので、デプロイ時に必ず設定してください（[security.md](./security.md#信頼境界とアクセス制御)）。

## 落とし穴集（不変条件ではないが、知らないと踏むもの）

| # | 落とし穴 |
|---|---|
| P-1 | **`tsc -b` だけでは Workers の型エラーが出ない。** 必ず `npm run typecheck` を使う |
| P-2 | **`workers/` で `@/` エイリアスは使えない。** 相対パスで書く |
| P-3 | **`wrangler.toml` は git 管理外。** バインディングや Cron や vars を変えたら `wrangler.toml.example` も同期して更新する |
| P-4 | **D1 マイグレーションは番号順に 1 ファイルずつ `--remote` 適用する。** `d1 migrations apply` は使わない |
| P-5 | **`wrangler pages deploy` の `--branch` を省略しない。** direct upload では対象ブランチでデプロイ先が変わる。Production ブランチは実環境で人間が確認して明示する |
| P-6 | **dev モードでは Service Worker が動かない**（仕様）。SW / Push の確認は `npm run build` の後に `npm run preview` を別々に実行する |
| P-7 | **ローカル D1 の消費量を自動計測する仕組みはリポジトリにない。** `rows_read` / `rows_written` や外部 fetch 数が必要な変更では、隔離した計測コードまたは自動テストを用意し、観測方法を記録する（[local-verification.md](./local-verification.md)） |
| P-8 | **ローカルの miniflare はプランの上限（50 クエリ等）を強制しない。** ローカルで通っても本番で上限に当たることがある |
| P-9 | **`sort_order` は INTEGER 列だが実際には REAL が入る**（fractional 採番）。SQLite の型アフィニティに依存している |
| P-10 | **`updated_at` はクライアント申告値。** 端末の時計が狂っていると LWW が壊れる。未来へ寄りすぎた値は `isValidPayload` が 366 日で足切りする |
| P-11 | **`Promise.allSettled` が例外を握り潰す。** `notify.ts` の前進処理で例外が出ても静かに失敗するだけなので、`wrangler tail` で見ないと気づけない |
| P-12 | **Windows + OneDrive 配下で `vite build` が `STATUS_STACK_BUFFER_OVERRUN` で落ちる。** OneDrive 外へ退避してビルドする |
| P-13 | **公開する Markdown は LF で追跡する。** `.gitattributes` が `*.md` を LF に固定する。既存の非 Markdown の改行を、無関係な変更で一括変換しない |
| P-14 | **`docs/` は Git 追跡対象かつ公開予定。** 実同期コード、鍵、購読 endpoint、利用者データ、バックアップ、ログ生値を置かない |
